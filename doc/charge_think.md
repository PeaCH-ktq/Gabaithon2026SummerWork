# 運用コスト試算（1,000 ユーザー想定）

TanE を実サービスとして 1,000 人の大学生に提供した場合の月額・年額維持費の概算。
調査日: 2026-09-03 / 為替レート: **1 USD = 160 円**（2026-09-02 時点 158.9 円を切り上げ）

> この文書は「いくらかかるか」だけでなく「**何が効いているか**」を残すことを目的とする。
> 前提値（節1）を差し替えれば全体が再計算できる形にしてある。

---

## 0. 結論（先に数字）

| シナリオ | 年額 | 月平均 | ピーク月 | ユーザー1人あたり/年 |
| --- | ---: | ---: | ---: | ---: |
| 楽観（軽量モデル＋前処理最適化） | **約 12 万円** | 約 1.0 万円 | 約 1.6 万円 | 約 120 円 |
| **標準（現状構成のまま有料枠へ移行）** | **約 27 万円** | 約 2.3 万円 | 約 4.6 万円 | 約 271 円 |
| 悲観（ヘビーユース＋大きい資料） | **約 73 万円** | 約 6.1 万円 | 約 14 万円 | 約 730 円 |

- 費用の **6〜9 割が Gemini API**。Supabase / Vercel は 1,000 人規模では最低プラン内にほぼ収まる。
- したがって**コスト管理＝問題生成 API の管理**であり、DB のチューニングではない。
- 年間費用の **半分以上が試験期の 4 か月（5・7・11・1 月）に集中**する。従量課金なので、
  この山をならす仕組み（後述の「日頃復習割」は課金設計としてだけでなくコスト平準化としても効く）。

## 1. 前提条件

### 1.1 利用形態の前提（日本の大学の年間サイクル）

登録ユーザー 1,000 人を固定とし、月を 3 種類に分類する。

| 区分 | 該当月 | アクティブ率 | 1人あたり月間生成回数 | 月間生成回数 |
| --- | --- | ---: | ---: | ---: |
| **ピーク**（中間・期末） | 5・7・11・1 月 | 70%（700人） | 8 回 | **5,600 回** |
| **通常**（学期中） | 4・6・10・12 月 | 40%（400人） | 2 回 | **800 回** |
| **閑散**（長期休暇） | 2・3・8・9 月 | 15%（150人） | 0.5 回 | **75 回** |

年間の問題生成回数 = (5,600 + 800 + 75) × 4 = **約 25,900 回/年**

> 根拠: 春学期は 4〜7 月（中間 5 月・期末 7〜8 月頭）、秋学期は 10〜1 月（中間 11 月・期末 1〜2 月頭）。
> 8 月後半〜9 月と 2 月後半〜3 月は長期休暇でほぼ止まる。ピーク月のアクティブ率が高いのは
> 「テスト前だけ課金して使う」という本アプリの想定利用動機そのもの。

### 1.2 1 回の問題生成で消費するトークン（標準シナリオ）

現行実装（[`lib/gemini/generateQuestions.ts`](../lib/gemini/generateQuestions.ts)）は
**Files API に PDF をそのまま上げて `generateContent` に渡す**。PDF は 1 ページ ≒ 258 トークン相当
（画像扱い）で課金されるため、入力トークンはページ数に比例する。

| 項目 | 標準 | 根拠 |
| --- | ---: | --- |
| 講義資料 PDF | 12,000 tok | 20 ページ級（上限は [`MAX_MATERIAL_BYTES`](../lib/gemini/config.ts) = 4MB） |
| プロンプト＋`responseSchema` | 1,500 tok | [`lib/gemini/prompts.ts`](../lib/gemini/prompts.ts) ＋構造化出力スキーマ |
| 追加指示 | 500 tok | 上限 1,000 字 |
| **入力 計** | **14,000 tok** | |
| 出力（問題 5〜10 問 + 解答 + 解説 + SVG figure + LaTeX） | 4,000 tok | SVG と KaTeX ラベルが重い |
| 思考トークン（Gemini 3.x 系は出力側で課金） | 3,000 tok | |
| **出力 計** | **7,000 tok** | |

**リトライ／フォールバック overhead を +10%** として計上する
（[`GENERATION_RETRY`](../lib/gemini/config.ts) の 503 バックオフ最大 3 回 ＋ `GEMINI_FALLBACK_MODEL` 切替）。

### 1.3 データ量の前提

| 項目 | 値 | 備考 |
| --- | ---: | --- |
| `question_sets.content`（jsonb）1 件 | 約 20 KB | SVG 込み。年間 25,900 件 → 約 520 MB（索引込み約 0.8 GB） |
| `materials` 1 ファイル | 平均 2 MB | 上限 4 MB |
| 1 ユーザーの年間アップロード | 30 ファイル | → Storage 年間増加 **約 60 GB** |
| 他テーブル（shelves/groups/sessions 等） | 無視できる | 全部合わせても数十 MB |

## 2. Gemini API

### 2.1 単価（有料枠 Standard、2026-09 時点）

| モデル | 入力 / 1M tok | 出力 / 1M tok | 本アプリでの位置づけ |
| --- | ---: | ---: | --- |
| `gemini-3.6-flash`（現行既定） | $0.75 | $3.75 | 標準シナリオで採用 |
| `gemini-2.5-flash`（現行 fallback） | $0.30 | $2.50 | コスト半減の第一候補 |
| `gemini-2.5-flash-lite` | $0.10 | $0.40 | 楽観シナリオ。品質検証が必要 |
| Batch API | 上記の **50% off** | 同左 | 非同期生成にすれば適用可 |

> **無料枠は本番では使えない**。RPD / RPM 制限があり、ピーク月の 5,600 回（≒ 1 日あたり 180 回、
> 試験直前は時間帯集中でさらに跳ねる）は確実に 429 に当たる。README の「本番運用時は有料枠へ」の通り。

### 2.2 1 回あたりの単価

`gemini-3.6-flash` の場合:

```
入力  14,000 tok × $0.75 / 1M = $0.0105
出力   7,000 tok × $3.75 / 1M = $0.0263
小計                          = $0.0368
リトライ overhead +10%        = $0.0405  ≒ 6.5 円/回
```

| モデル | 1回あたり | 円換算 |
| --- | ---: | ---: |
| `gemini-3.6-flash` | $0.0405 | **約 6.5 円** |
| `gemini-2.5-flash` | $0.0239 | 約 3.8 円 |
| `gemini-2.5-flash-lite` | $0.0047 | 約 0.8 円 |

### 2.3 月別・年間コスト（標準 = 3.6-flash）

| 区分 | 生成回数/月 | 月額 (USD) | 月額 (円) | 年間該当月数 | 年額 (円) |
| --- | ---: | ---: | ---: | ---: | ---: |
| ピーク | 5,600 | $227 | 36,300 | 4 | 145,200 |
| 通常 | 800 | $32 | 5,200 | 4 | 20,800 |
| 閑散 | 75 | $3 | 500 | 4 | 2,000 |
| **合計** | | | | | **約 168,000 円/年** |

Files API のアップロード自体は無料（48 時間で自動失効、生成後に
[`deleteMaterial`](../lib/gemini/files.ts) で即削除しているので保管コストも発生しない）。

## 3. Supabase

### 3.1 プランと 1,000 ユーザーでの消費量

Pro プラン **$25/月**（= 4,000 円/月）を前提とする。Free プランは 1 週間無アクティブで
プロジェクトが一時停止するため本番運用不可。

| リソース | Pro 込み | 本アプリの想定消費 | 判定 |
| --- | ---: | ---: | --- |
| MAU | 100,000 | 最大 700 | 余裕 |
| DB サイズ | 8 GB | 年 +0.8 GB | 余裕（約 8 年分） |
| Storage | 100 GB | 年 +60 GB | **2 年目で超過** |
| Egress | 250 GB | ピーク月 約 45 GB | 余裕 |
| Cached Egress | 250 GB | 少 | 余裕 |
| Compute クレジット | $10（Micro 1台分） | Micro で足りる想定 | ピーク月のみ要注意 |

**Egress の内訳（ピーク月）**

| 経路 | 計算 | 量 |
| --- | --- | ---: |
| 問題生成時のサーバー側ダウンロード | 5,600 回 × 2 MB | 11 GB |
| ユーザーの資料閲覧 | 700人 × 20 回 × 2 MB | 28 GB |
| API/JSON（問題集・棚・グループ） | — | 約 5 GB |
| **計** | | **約 44 GB** |

250 GB に対して余裕がある。ただし「資料をブラウザで何度も開き直す」使い方が増えると
一番早く効いてくる項目なので、署名付き URL のキャッシュ設定は入れておきたい。

### 3.2 超過見込みと年額

| 項目 | 金額 |
| --- | ---: |
| Pro プラン $25 × 12 | 48,000 円 |
| ピーク 4 か月のみ Micro → Small（+$5） | 3,200 円 |
| Storage 超過（2 年目以降 +60GB × $0.0213） | 約 2,500 円/年 |
| **合計** | **約 48,000 円（1年目）／ 約 54,000 円（2年目以降）** |

**コンピュートの注意点**: Micro（1 GB RAM / 直接接続 60 / プーラー 200）は
1,000 人規模の平常時には十分だが、試験直前の同時アクセス集中では接続枯渇の可能性がある。
本アプリはブラウザから `supabase-js` で直叩き（RLS で認可）する設計
（[`doc/database.md`](database.md) 「RLS 直叩き ＋ 必要な所だけ Route Handler」）なので、
**同時接続数がそのままユーザー数に比例する**点に注意。ピーク月だけ Small に上げる運用が現実的。

## 4. Vercel

| 項目 | 内容 |
| --- | --- |
| Pro プラン | $20/月/デプロイシート（$20 分の利用クレジット込み） |
| 込みの帯域 | Fast Data Transfer 1 TB、Edge Requests 1,000万 |
| 懸念 | **問題生成 Route Handler の実行時間**（Gemini 応答待ちで 20〜60 秒／回、Node ランタイム） |

ピーク月の関数実行時間 = 5,600 回 × 40 秒 ≒ 62 GB-hours。
帯域と Edge Requests は 1,000 人規模なら込みの枠を使い切らない。関数側で
クレジットを食い切る月がある想定で、ピーク 4 か月は +$15 程度を見込む。

| 項目 | 金額 |
| --- | ---: |
| Pro $20 × 12 | 38,400 円 |
| ピーク月の関数超過 $15 × 4 | 9,600 円 |
| **合計** | **約 48,000 円/年** |

> シートは「デプロイする人」の数で課金される。ハッカソンチームがそのまま運用に入る場合、
> 実際にデプロイするメンバーだけをシートに載せること（人数分だけ月額が増える）。

## 7. コスト削減の打ち手（効果の大きい順）

1. **PDF をテキスト抽出してから渡す（効果: 入力トークン 1/3）**
   現状は PDF を Files API にそのまま上げているため 1 ページ ≒ 258 トークンの画像課金になる。
   図が不要な資料はサーバー側でテキスト抽出してから渡せば入力が大幅に減る。
   （図表が問題生成に必要な資料もあるので、全面適用ではなく判定が要る）

2. **モデルの出し分け（効果: 40〜90% 減）**
   無料/軽量ユーザーは `gemini-2.5-flash` または `flash-lite`、課金ユーザーのみ `3.6-flash`。
   [`GEMINI_MODEL`](../lib/gemini/config.ts) は env で差し替え可能な設計になっているので、
   リクエスト単位でモデルを選べるよう引数化するだけで済む。

3. **ユーザー単位のレート制限（効果: 悲観シナリオの回避）**
   現状 [`POST /api/questions/generate`](../app/api/questions/generate/route.ts) には
   認証はあるがユーザー単位の生成回数制限がない。**1 人が連打するだけで青天井**なので、
   「無料は月 3 回 / 有料は月 30 回」のようなクォータは課金設計以前に事故防止として要る。

4. **同一資料からの重複生成をブロック（効果: 10〜20% 減）**
   `question_sets.source_material_id` に既存行があれば「前に作った問題集を開く」へ誘導する。
   試験直前は同じ資料を何度も投げる行動が起きやすい。

5. **Batch API の活用（効果: 該当分 50% 減）**
   「資料をアップしておけば夜のうちに問題集ができている」という UX に寄せられるなら、
   バッチ単価が使える。即時生成と併存させ、無料枠はバッチのみにするのも手。

6. **Storage の保持期間（効果: 2 年目以降の超過回避）**
   `materials` は生成後に必須ではない（問題集は jsonb で別に永続化済み）。
   学期終了後 6 か月で削除するポリシーを入れれば Storage は 100 GB 以内で頭打ちになる。

7. **試験期の Supabase コンピュート増強を予約運用**
   ピーク 4 か月だけ Small、それ以外は Micro。年 3,000 円程度の追加で接続枯渇を防げる。

## 8. 収支の目安

想定コスト **月平均 22,000 円 / ピーク月 46,000 円**。

| 課金設計 | 黒字化に必要な有料ユーザー |
| --- | --- |
| 月額 300 円 | 月平均 74 人（7.4%）／ピーク月 154 人（15.4%） |
| 月額 500 円 | 月平均 44 人（4.4%）／ピーク月 92 人（9.2%） |
| 学期パック 1,500 円（4か月） | 学期あたり 約 90 人 |

「テスト期間だけ課金する」利用者が主体になると、**コストの山と売上の山は同じ月に来る**ので
キャッシュフロー上は素直。一方 README にある **「日頃復習割」**（学期契約 ＋ 週1利用で割引）は、
売上を平準化するだけでなく、閑散期に安いモデルで生成させることで
**ピーク月の単価の高い生成を減らす**効果もある。コスト面から見ても筋が良い。

## 9. この試算のリスク・未確定事項

- **トークン数は実測していない**。節 1.2 は設計からの見積り。ピーク前に
  `usageMetadata`（`generateContent` のレスポンス）をログに残して実測に差し替えること。
  1 回あたり単価が 2 倍になれば年額は +17 万円。
- **Gemini の価格改定リスク**。Flash 系の単価はモデル世代ごとに動いている
  （3.6-flash $0.75/$3.75 に対し 3-flash preview は $0.50/$3.00）。既定モデルを
  env で切り替えられる現行設計は、この点で正しい。
- **思考トークン**は制御していない。Gemini 3.x 系は出力側で課金されるため、
  thinking budget を絞れるならさらに下げられる余地がある。
- **Vercel の関数コスト**は実行時間の実測がないため最も粗い見積り。Gemini 応答待ちが
  そのまま課金時間になるので、生成が遅いモデルほど二重にコストが乗る点に注意。
